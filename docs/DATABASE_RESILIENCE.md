# Database availability: cloud and intranet

The AWS deployment and each intranet deployment own separate PostgreSQL databases.
An intranet installation must not point to AWS if it needs to operate without internet.
There is no automatic cross-site write failover or database synchronisation.

Auth, meeting and migration connections share `shared/database.cjs`:
- Maximum 10 connections per process; size total replicas against database capacity.
- Connection acquisition expires in 3 seconds; SQL statements in 5 seconds.
- Lock waits expire in 2 seconds; idle transactions are terminated after 10 seconds.
- Client query timeout is 8 seconds. A timed-out write can have an uncertain outcome;
  do not automatically retry writes without an idempotency key or reconciliation.
- Idle connection failures are handled; subsequent requests reconnect through pg.
- `/health` checks process liveness; `/ready` checks the database and returns 503 on failure.
- Remote connections verify certificates. Configure POSTGRES_CA_FILE for RDS.
  Explicit POSTGRES_SSL=disable is only for a trusted intranet/local development network.
- Migration processes use a PostgreSQL advisory lock to prevent concurrent schema changes.

Run `npm run db:migrate` from the repository root; the runner loads the private root .env.
Use the RDS endpoint hostname, not its current IP, so reconnection follows DNS changes.

These bounds prevent indefinite normal connection/query waits. They do not guarantee
availability during machine failure, resource exhaustion, network partitions or data loss.
Existing API error responses are preserved; not all DB errors have a uniform 503 response.

## Before production

Cloud: private RDS with backend security-group-only access; verified TLS, an application
role with only required privileges, automated backups and a tested point-in-time restore.
Single-AZ demo RDS has no standby; Multi-AZ requires a separately approved cost estimate.
Monitor database connections, CPU, free storage, replica lag (if used), and readiness.
Application health checks must use /ready for routing, /health for process restarts.

Intranet: local database/storage and locally available identity/language dependencies.
Provide UPS power, local backups on another device and a tested restore procedure.
A second local PostgreSQL server with managed replication/failover is needed for host HA.
Travelling access uses the organisation's VPN; an office internet outage blocks remote
access but must not redirect local writes to a cloud database.

Backups, failover, VPN, replication, alarms and restore drills are deployment work;
this source change does not provision or prove them.
